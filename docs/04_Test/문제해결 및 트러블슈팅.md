# 문제 해결 및 Troubleshooting

CUBIC 개발 과정에서는 단순한 소프트웨어 오류뿐 아니라, 부품 데이터 부족, 센서 신호 왜곡, 통신 병목, 주행 오차 등 하드웨어와 소프트웨어가 복합적으로 얽힌 문제가 발생하였다.
각 문제에 대해 측정과 로그 분석을 통해 원인을 확인하고, 하드웨어 및 소프트웨어 양쪽에서 해결 방법을 적용하였다.

## 1. 모터 데이터시트 정보 부족

### 문제

사용한 기어드 BLDC 모터의 데이터시트에는 실제 제어에 필요한 FG 출력 특성, 펄스 수, 드라이버 동작 조건 등의 정보가 충분히 제공되지 않았다.

### 원인 분석

단순히 정격 RPM과 전압 정보만으로는 실제 속도 제어와 오도메트리 계산에 필요한 FG 신호 특성을 결정할 수 없었다.

### 해결

모터를 직접 구동하며 오실로스코프와 MCU를 이용해 FG 파형과 출력 주파수를 측정하였다.
이를 기반으로 FG 펄스 수와 실제 출력 RPM 관계를 역산하여 제어 파라미터를 결정하였다.

### 결과

외부 데이터에 의존하지 않고 실제 모터 특성에 맞는 속도 측정 및 제어값을 확보할 수 있었다.

---

## 2. FG 신호 왜곡 및 속도 측정 불안정

### 문제

모터의 FG 출력 신호가 MCU에서 안정적인 디지털 신호로 인식되지 않아 RPM 값이 튀거나 잘못 계산되는 문제가 발생하였다.

### 원인 분석

FG 출력에 전압 스파이크와 불안정한 전압 구간이 존재했으며, PC817 옵토커플러를 통한 절연 이후에도 출력 전압이 완전한 디지털 High/Low 형태로 형성되지 않았다.

### 해결

FG 신호를 ADC로 직접 샘플링하고, High/Low 판정에 서로 다른 임계값을 사용하는 **히스테리시스 방식**을 적용하였다.
또한 ADC 샘플링과 DMA를 이용하여 신호를 지속적으로 수집하고 펄스를 검출하도록 구성하였다.

### 결과

노이즈 구간에서 발생하던 오검출이 감소하였으며, 안정적인 FG 펄스 측정과 RPM 계산이 가능해졌다.

---

## 3. 상위 제어기와 MCU 간 통신 병목

### 문제

초기 ROS 2 연동 과정에서 명령 전달과 센서 데이터 반영이 늦어지고, Foxglove를 통한 조작에서도 약 1초 수준의 지연이 발생하였다.

### 원인 분석

MCU 내부에서 통신 처리와 모터 제어, FG 측정 작업이 하나의 실행 흐름에 집중되어 있어 실시간 제어 주기가 영향을 받았다.

### 해결

RP2350의 듀얼 코어 구조를 활용하여 역할을 분리하였다.

* Core 0: micro-ROS 통신, FG 측정, 명령 처리
* Core 1: 가속 제한, 기동 제어, 속도 제어, PWM 출력

전원 제어기 역시 통신과 센서 처리를 분리하여 상위 시스템과의 데이터 교환이 제어 루프를 방해하지 않도록 구성하였다.

### 결과

명령 응답 지연이 크게 감소하였으며, 모터 제어와 ROS 2 통신을 동시에 안정적으로 수행할 수 있게 되었다.

---

## 4. 부팅 시 모터 순간 동작

### 문제

전원 인가 직후 MCU가 초기화되는 동안 모터가 짧게 움직이는 현상이 발생하였다.

### 원인 분석

MCU GPIO가 초기화되기 전 PWM 및 DIR 관련 신호가 순간적으로 불확정 상태가 되면서 모터 드라이버가 이를 유효한 입력으로 인식하였다.

### 해결

소프트웨어 초기화 과정에서 PWM 출력이 활성화되기 전에 모든 제어 출력을 안전 상태로 설정하도록 하였으며, 모터 정지 상태를 기본값으로 사용하였다.
또한 비상정지 스위치는 MCU 상태와 관계없이 모터 전원을 직접 차단하도록 별도의 하드웨어 안전 계층으로 유지하였다.

### 결과

부팅 과정에서 발생할 수 있는 비정상 구동 위험을 줄이고, 제어 소프트웨어와 독립적인 안전 구조를 확보하였다.

---

## 5. 정지 시 관성에 의한 오도메트리 오차

### 문제

주행 후 정지할 때 로봇이 관성에 의해 일부 미끄러지지만 모터 FG 신호는 이미 정지 상태로 판단되어, 실제 이동량과 휠 오도메트리 사이에 차이가 발생하였다.

### 원인 분석

현재 모터 구조에서는 PWM이 0이 되면 FG 출력 역시 사라지기 때문에, 전원이 제거된 이후 발생하는 자유 회전 또는 슬립을 직접 측정할 수 없다.

### 해결

급격한 정지를 피하도록 PWM을 단계적으로 감소시키고, SLAM 및 LiDAR 기반 위치 보정을 함께 사용하였다.
IMU 가속도 기반 보정도 시험하였으나 지도 정합이 오히려 악화되는 경우가 있어 최종 구성에서는 제외하였다.

### 결과

현재 하드웨어 조건에서 완전한 관성 이동 측정에는 한계가 있음을 확인하였으며, 제어 감속과 외부 센서 기반 보정을 조합하는 방식으로 안정성을 확보하였다.

---

## 6. LiDAR 및 TF 정합 문제

### 문제

초기 SLAM 구성에서 지도상의 로봇 위치가 실제 위치와 다르게 보이거나, 전방·후방 LiDAR 데이터가 올바르게 겹치지 않는 문제가 발생하였다.

### 원인 분석

LiDAR 장착 방향과 TF 좌표계, `base_link` 기준 위치가 실제 기구 배치와 일치하지 않는 경우 스캔 데이터가 반전되거나 회전된 형태로 나타났다.

### 해결

실제 CAD 및 장착 위치를 기준으로 URDF/Xacro의 센서 위치와 방향을 다시 확인하였다.
전방 및 후방 LiDAR의 yaw 방향을 구분하고, 로봇 자체 구조물을 감지하는 영역은 스캔 마스킹을 적용하였다.

### 결과

두 LiDAR의 스캔이 `base_link` 기준으로 정상 정합되었고, 병합된 `/scan` 데이터를 이용한 SLAM 품질이 개선되었다.

## 7. ROS 2 서비스 및 부팅 순서 문제

### 문제

부팅 시 micro-ROS agent, LiDAR, IMU, SLAM, Foxglove 등의 서비스가 서로 다른 시점에 시작되면서 일부 노드가 정상적으로 연결되지 않는 문제가 발생하였다.

### 원인 분석

단순히 systemd 서비스 실행 순서만 지정해서는 ROS 2 토픽과 노드가 실제 사용 가능한 상태가 되었는지 보장할 수 없었다.

### 해결

각 하위 제어기와 센서 서비스를 독립적으로 구성하고, 필요 시 ROS 2 토픽 생성 여부를 기준으로 시스템 준비 상태를 판단하도록 하였다.
또한 Mapping과 Navigation 기능을 별도 서비스로 분리하여 필요하지 않은 노드를 동시에 실행하지 않도록 구성하였다.

### 결과

부팅 과정의 의존성을 단순화하고, 각 기능을 독립적으로 재시작하거나 점검할 수 있는 구조를 확보하였다.

---

## 정리

CUBIC의 주요 문제들은 특정 부품 하나의 결함보다는 **기계 구조, 전기 신호, MCU 펌웨어, ROS 2 통신이 서로 연결되어 발생하는 복합적인 문제**가 대부분이었다.

따라서 개발 과정에서는 다음 원칙을 중심으로 문제를 해결하였다.

* 실제 신호와 데이터를 직접 측정하여 원인 확인
* 하드웨어와 소프트웨어 문제를 분리하여 분석
* 제어와 통신의 실행 구조 분리
* TF 및 센서 위치를 실제 기구 설계와 일치
* 안전 기능은 소프트웨어에만 의존하지 않고 하드웨어에서도 보장
* 해결 효과가 없는 보정 알고리즘은 과감히 제거

이러한 과정은 CUBIC을 단순히 동작하는 로봇이 아니라, **문제 원인을 분석하고 수정할 수 있는 재현 가능한 로봇 플랫폼**으로 만드는 데 중요한 기반이 되었다.
